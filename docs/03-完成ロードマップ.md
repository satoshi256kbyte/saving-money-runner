# Saving Money Runner 完成ロードマップ

## 目的

本書は、Saving Money Runnerを顧客AWSアカウントへ安全に導入できるMVPから、
本番提供可能なリリースまでの実装順序を定める。各タスクは、1回のSpec Kitサイクル
（specify、clarify、plan、tasks、analyze、implement）で完了させる粒度とする。

Issueはタイトルの`[P番号][順序]`で優先度と実施順を示す。番号が小さいIssueを先に着手し、
依存先のIssueが完了してから次のIssueへ進む。

## 完成の定義

次の条件をすべて満たした状態をMVP完成とする。

- 顧客AWSアカウント内に、Private Subnet上のエフェメラルGitHub Actionsランナーを構築できる
- GitHub AppのWebhookをHMAC検証し、正当なジョブだけを処理できる
- ランナーは1ジョブ単位で破棄され、ジョブ間でワークスペースや認証情報を再利用しない
- AWS CDKでAWSリソースとGitHub連携を再現可能に構築できる
- MinistackとCIで、正常系・異常系・権限境界を実AWSなしで検証できる
- AMIを定期更新し、検査と承認を通過した版だけをランナーへ配布できる
- CloudTrail、CloudWatch、コスト上限・異常通知を含む運用手順がある
- 初回導入、更新、ロールバック、撤去の手順をドキュメント化している
- 顧客向けのブランチE2Eとリリース判定を再現できる

## 対象外

GitLab CI/CD対応、Jenkins対応、複数顧客を共有するコントロールプレーン、
AWS Marketplace公開はMVP完成後の拡張とする。MVPではGitHub Actionsと顧客単位の
AWSアカウント分離に集中する。

## IssueごとのSpec Kit境界

### 01 開発基盤と品質ゲート

AWS CDKのディレクトリ構成、PNPMの依存管理、基本CI、Ministackの起動、
AWS CDK synth、テスト実行方法を定める。AWSリソースの本実装は含めない。

依存先はない。02以降の全タスクが利用する基盤を完成させる。

### 02 脅威モデルとセキュリティ基準

GitHub、顧客AWSアカウント、Webhook、Lambda、ランナー、AMIビルドを信頼境界として整理し、
攻撃経路、保護対象、許容リスク、最小権限、ログ保持、失敗時の停止条件を定める。

01に依存する。03から07の設計判断を確定する入力とする。

### 03 GitHub AppとWebhook登録

顧客Organization限定のPrivate App、必要最小限の権限、Webhook URL、Webhook Secret、
Secrets Manager保存、AWS CDK管理方法を実装する。GitHub連携に必要な機能がAWS CDKだけで不足する場合は、
安全な導入CLIとの責務境界をSpecで確定する。

01、02に依存する。04、05、11が利用する契約を提供する。

### 04 Webhook受信と署名検証

API GatewayとLambdaでWebhookを受信し、HMAC署名、イベント種別、リプレイ、タイムスタンプ、
入力サイズ、冪等性を検証する。不正リクエストはランナーを起動せず、監査可能な診断を残す。

01、02、03に依存する。05、08、10が利用するイベント処理を完成させる。

### 05 ランナー登録オーケストレーション

検証済みWebhookから対象リポジトリ・ラベル・ジョブ情報を抽出し、GitHubの短命な登録トークンを
取得してランナー起動要求へ渡す。重複イベント、トークン取得失敗、タイムアウト、キャンセルを
安全に処理する。

01、02、03、04に依存する。07と08が利用する制御プレーンを完成させる。

### 06 VPCとIAMのセキュリティ基盤

ランナーをPrivate Subnetへ配置し、必要なAWS APIと外部通信だけを許可する。Lambda、ランナー、
AMIビルドのIAM Roleを分離し、Secrets Manager、EC2、Auto Scalingへの権限を最小化する。
CloudTrailと必要なVPC BPA除外の扱いも確定する。

01、02に依存する。07、09、10、12が利用するAWS基盤を完成させる。

### 07 EC2 Spotエフェメラルランナー

承認済みAMIからEC2 Spotを起動し、1ジョブ1ランナーのライフサイクルを実装する。起動失敗、
Spot中断、ジョブ失敗、強制終了、残存リソース、ワークスペース汚染を扱い、Auto Scalingとの
責務分担を定める。

01、02、05、06に依存する。08、09、10、12が利用する実行基盤を完成させる。

### 08 ローカル結合テストと権限境界検証

MinistackでWebhookからLambda、ランナー起動要求までを再現する。正しい署名、不正な署名、
リプレイ、権限不足、タイムアウト、重複イベントをテストし、CIのクリーン環境で再実行可能にする。

01、04、05、06、07に依存する。実AWSに依存しないリグレッションゲートを完成させる。

### 09 AMIビルドと安全なローリング更新

EC2 Image BuilderでOSハードニングとパッチ適用を行い、脆弱性検査、承認、世代管理、
ロールバック、ローリング更新を実装する。未承認AMIや検査失敗のAMIをランナーへ配布しない。

01、02、06、07に依存する。12の本番検証で利用する更新経路を完成させる。

### 10 監視、監査、コスト制御

CloudWatchのログ・メトリクス・アラーム、CloudTrailの監査証跡、Webhookからランナーまでの
相関ID、Spot中断と起動失敗の通知、AWSコスト異常の検知を定める。ログへシークレットやジョブ内容を
出さないマスキング方針も検証する。

01、02、04、05、06、07に依存する。運用時の検知と調査を完成させる。

### 11 導入・更新・撤去CLIと運用文書

PNPMで提供するCLIまたはスクリプトに、事前検査、AWS CDK実行、GitHub設定、出力確認、
更新、ロールバック、撤去を実装する。必要なAWS権限、確認値、秘密情報の扱い、失敗時の復旧を
顧客向け文書に記載する。

03、06、07、09、10に依存する。顧客が自己完結で運用できる導入経路を完成させる。

### 12 本番E2Eとリリース判定

顧客AWSアカウント相当の隔離環境へデプロイし、GitHub workflow実行、ランナーの使い捨て、
不正Webhook拒否、AMI更新、監視通知、ロールバック、撤去を検証する。アカウントIDやARNを公開証跡へ
残さない。未達時はリリースせず、再実装が必要なIssueへ分解する。

08、09、10、11に依存する。MVP完成を判定する最終タスクとする。

## 各Issueで必ず実施するSpec Kit手順

各Issueでは、次の順序を省略しない。

1. `specify`で対象Issueの要件と受け入れ条件を`spec.md`にする
2. `clarify`で未決事項、権限境界、失敗時の出力契約を解消する
3. `plan`で技術方針、変更範囲、検証境界を定める
4. `tasks`で実装・テスト・文書化の作業を分解する
5. `analyze`で要件、計画、タスクの整合性とカバレッジを確認する
6. CriticalまたはHighの指摘を解消してから`implement`へ進む
7. 実装後に受け入れ条件、セキュリティ検査、回帰テストを確認する

## 優先度の扱い

| 優先度 | 意味 | 扱い |
| --- | --- | --- |
| P0 | MVPの成立または安全性に必須 | 先行して完了させ、未達なら後続をリリース対象にしない |
| P1 | 本番運用に必須 | P0完了後に実施し、MVPリリース前に完了させる |
| P2 | MVP後の拡張 | GitLab対応、Marketplace公開などを別ロードマップで扱う |

Issue作成後は、本書の実施順表にIssue番号とリンクを反映する。Issue間の依存関係は、各Issue本文の
`依存先`と`後続タスク`にも記載し、順序がIssue単体でも確認できる状態にする。
