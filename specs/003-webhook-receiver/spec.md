# GitHub Webhook受信基盤

## 背景

Saving Money Runnerは、顧客Organizationに導入したPrivate GitHub Appからの Webhook を受信し、
GitHub Actionsのジョブ要求に応じてランナーを用意する。
Issue #3（`specs/002-github-app-webhook`）は、Webhook SecretのSecrets Manager管理と設定契約までを確定した。
Webhookを受信する経路は、インターネットから到達できる入口になる。
そのため、署名検証を通過しない入力が後続処理へ到達しないことを、この Spec で固定する。

## 目的

API GatewayとLambdaでGitHub Webhookを安全に受信する。
HMAC署名、イベント種別、リプレイ、重複を検証し、検証済みイベントだけを後続のIssue #5へ渡す。
成功、拒否、再試行のHTTP応答と診断を契約として固定する。

## スコープ

### 対象

- API GatewayによるWebhook受信エンドポイントの提供
- Lambdaによるリクエスト検証と後続処理への引き渡し
- raw bodyに対するHMAC-SHA256署名の定数時間比較による検証
- リプレイ防止
- 本文ダイジェスト（bodyDigest）による重複排除
- 拒否理由と成功、再試行の診断、およびHTTP応答の契約
- CloudFormation Output `GitHubAppWebhookUrl` の提供
- Webhook処理だけに限定したSecret読取り権限の付与

### 対象外

- GitHub Actionsランナーの起動と停止（Issue #5以降）
- GitHub APIの呼び出し
- 実AWS環境へのデプロイ
- 実際のGitHub Appへの Webhook URL 登録
- Webhook Secretの作成と実値の管理（Issue #3の成果物）
- Secretの自動ローテーション実装（別Specで扱う。Q-006）

## 入力契約

### 受信するヘッダー

| ヘッダー | 用途 | 必須 | 備考 |
| --- | --- | --- | --- |
| `X-Hub-Signature-256` | HMAC-SHA256署名（`sha256=<hex>` 形式） | 必須 | 欠落、形式不正、不一致は拒否する |
| `X-GitHub-Event` | イベント種別 | 必須 | 許可するのは `workflow_job` と `ping`。`ping` は署名検証とJSON検証の後に200で受理し、後続へ渡さない（Q-009） |
| `X-GitHub-Delivery` | 配信ID（診断用。重複排除のキーにはしない） | 必須 | 欠落は拒否する。署名対象外のため、キーにしない（`clarify.md` Q-002） |
| `Content-Type` | ペイロード形式 | 必須 | `application/json` のみ想定する |
| `X-Hub-Signature` | SHA-1署名（旧形式） | 使用しない | 検証にも判断にも使わない |
| タイムスタンプ系ヘッダー | リプレイ防止 | 存在しない | GitHub Webhookは署名対象のタイムスタンプヘッダーを提供しない |

GitHub Webhookには、Stripeのような署名付きタイムスタンプがない。
このため、Issue #4の「期限切れ」は、署名対象のbodyの中にある時刻項目と、Lambdaの受信時刻との差で判定する。
差が3日（GitHubの再配信期間）を超えたら拒否する（Q-001、J-1）。時刻項目の選び方は `plan.md` に定める。

### raw bodyの扱い

- 署名はAPI Gatewayが受け取った生のバイト列に対して計算する。JSONのパースや再シリアライズ後の値では検証しない。
- base64エンコードされた body（`isBase64Encoded`）は、検証前にバイト列へ戻す。
- 署名検証が成功するまで、bodyの内容をログ、診断、後続処理へ渡さない。
- 検証後にJSONとしてパースし、許可したイベントの必要項目だけを後続へ渡す。

## 機能要件

Issue #4の受け入れ条件を、1件ずつ要件にする。

- **FR-001** GitHubの署名（`X-Hub-Signature-256`）をraw bodyに対してHMAC-SHA256で計算し、定数時間比較で検証する。
- **FR-002** 署名不正、Secret不在、期限切れ、入力超過、不正イベントの各入力を、ランナー起動なしで拒否する。
  拒否した入力は、後続処理へ渡さない。
- **FR-003** 配信ID（`X-GitHub-Delivery`）または同等のキーで、重複イベントを冪等に処理する。
  重複配信は後続へ二重に渡さない。
- **FR-004** リクエストと例外のログに、Secret、トークン、ジョブ内容を出さない。
- **FR-005** 成功、拒否、再試行の診断とHTTP応答を、契約テストで固定する。
- **FR-006** Issue #3から引き継いだWebhook URL、HMAC検証、ローテーション、Secret取得運用の契約を、
  `clarify.md` で固定する。
- **FR-007** CloudFormation Output `GitHubAppWebhookUrl` としてWebhook URLを出力する。
- **FR-008** Webhook Secretの読取り権限は、Webhook処理のLambdaロールだけに付与する。書き込み権限は付与しない。
- **FR-009** 検証済みイベントだけを、Issue #5が受け取れる形式で引き渡す。
  引き渡しは SQS 標準キューで行い、形式は `plan.md` の「後続メッセージの契約」に定める（Q-010、J-4）。
  配信は重複しうるため、Issue #5は bodyDigest を冪等キーとして処理する。
- **FR-010** 受付レート、バースト、Lambdaの予約同時実行数は、顧客ごとの必須設定とする。
  未指定ならデプロイを失敗させる（J-2）。body上限は設定可能とし、既定は6 MBとする（J-3。値は非機能要件の入力サイズ上限を参照）。

## 非機能要件

| 項目 | 要件 |
| --- | --- |
| 秘密値の保護 | Webhook Secret、署名の計算途中の値、トークンをログ、診断、Output、テンプレートへ出さない |
| 入力サイズ上限 | 上限を超えるbodyは署名検証の前に拒否する。上限は設定可能で、既定はLambda同期呼び出しの6 MB（6291456バイト。J-3）。API Gatewayの10 MBより6 MBが先に効く |
| タイムアウト | Lambdaタイムアウトは3秒（Q-008）。GitHubの10秒とAPI Gatewayの統合タイムアウトより短い |
| 再現性 | Context lookupを使わない。AWS認証なしでsynthと契約テストを実行できる |
| 最小権限 | Lambdaロールに許可するSecret操作は、固定のSecret ARNに対する読取りだけとする |
| 診断の安全性 | 拒否理由は分類コードで記録し、入力内容を含めない |
| 診断ログの保持期間 | Lambdaのロググループの保持期間は30日（J-5）。ロググループはCDKで明示的に作成する |
| 監査 | Secret取得はCloudTrailで追跡できる状態を保つ |

## 依存する既存の契約（Issue #3の成果物）

| 項目 | 契約 |
| --- | --- |
| Webhook Secret名 | 固定値 `saving-money-runner/github-app/webhook` |
| Secret ARN | CloudFormation Output `GitHubAppWebhookSecretArn`（実値は環境ごとに異なり、Specには書かない。表記は `<SECRET_ARN>`） |
| 読取り権限 | 管理者ロールと `additionalReaderRoleArns` に限定される。Webhook処理のLambdaロールは、同じStackで作るロールとして型付きで追加する（`plan.md`） |
| 設定ファイル | `config/github-app.example.json` の `webhookEvents` は `workflow_job` のみ |
| Webhook URL | 本Issueが `GitHubAppWebhookUrl` として提供する |
| GitHub Appの権限 | `Actions: read` と `Metadata: read` のみ。Administrationは付与しない |

Webhook処理に書き込み権限が必要になった場合は、本Specでは扱わず、別Specで再承認する。

## 受け入れ条件

検証は、AWS認証なしで実行できる自動テストで行う。

### 正常系

- 正しいSecretで計算した署名を持つ `workflow_job` イベントを受信すると、2xxを返し、後続への引き渡しが1回発生する。
- 成功を示す診断が記録され、診断にbodyの内容とSecretが含まれない。
- synth結果に `GitHubAppWebhookUrl` のOutputが存在する。
- LambdaロールのSecret権限が、`GitHubAppWebhookSecretArn` の対象だけへの読取りに限定される。

### 拒否系

| 入力 | 期待する結果 |
| --- | --- |
| 署名ヘッダーの欠落、形式不正、値の不一致 | 拒否する。後続への引き渡しは0回 |
| Secretの取得失敗（不在、権限なし） | 拒否または失敗応答を返す。後続への引き渡しは0回 |
| 受信時刻と本文の時刻項目の差が3日を超える配信 | 拒否する（J-1） |
| 入力サイズ上限の超過 | 署名検証の前に拒否する |
| `workflow_job` 以外のイベント種別、配信IDの欠落 | 拒否する |
| JSONとして不正なbody | 署名検証後に拒否する |

- 拒否時のログ、診断、例外に、Secret、トークン、ジョブ内容が含まれない。
- 拒否したいずれの入力でも、ランナー起動に相当する処理が呼ばれない。

### 再試行系

- 同じ本文を再受信した場合（配信IDが違っても）、後続への引き渡しは二重に発生せず、応答は契約で定めた重複時の応答になる。
- 後続への引き渡しが一時的に失敗した場合、GitHubが再配信できる応答（再試行を促すステータス）を返す。
  失敗した本文（bodyDigest）は、重複として扱わない。
- 再試行系の診断が、成功、拒否と区別できる分類で記録される。

### 契約の固定

- 成功、拒否、再試行のHTTPステータスと診断分類が契約テストで固定されている。
- ローテーション中に旧版のSecretで署名された配信を拒否しない方式が、`clarify.md` で固定されている。
- `corepack pnpm quality` が成功する。

## 未決事項と決定

clarify（`clarify.md`）で検討した結果を示す。根拠と詳細は `clarify.md` に記録している。
状態が「決定」の項目は変更しない。人の判断が必要だった J-1〜J-5 は、すべて決定済みである。

| 番号 | 論点 | 状態 | 内容 |
| --- | --- | --- | --- |
| Q-001 | タイムスタンプの許容時間 | 決定 | 受信時刻と本文の時刻項目の差が3日を超えたら拒否する（J-1）。GitHubの再配信期間を基準にする |
| Q-002 | 重複排除の保存先と保持期間 | 決定 | DynamoDBの条件付き書き込み。保持期間は処理時刻から3日（GitHubの再配信期間）。bodyは保存しない |
| Q-003 | Lambdaの同時実行とエラー応答 | 決定 | 応答と再試行の規則は決定。受付レートと予約同時実行数は顧客ごとの必須設定で、未指定ならデプロイを失敗させる（J-2） |
| Q-004 | Webhook URLの認証の要否 | 決定 | 署名検証のみを必須とする。IP制限とWAFは採用しない |
| Q-005 | API Gatewayの種類 | 決定 | HTTP API（payload format 2.0） |
| Q-006 | Secretローテーションの方式 | 決定 | 手動Runbookを正式契約とする。自動化は別Spec。切り替え中は `AWSCURRENT` と `AWSPENDING` を検証する |
| Q-007 | Secret取得運用 | 決定 | `docs/05` の登録手順と権限を運用契約とする。Webhook処理ロールは読取りのみ |
| Q-008 | 入力サイズ上限とタイムアウトの値 | 決定 | Lambdaタイムアウト3秒、Secretキャッシュ300秒。body上限は6 MBを既定とする設定値（J-3） |
| Q-009 | `ping` イベントの扱い | 決定 | 署名検証とJSON検証の後に200で受理し、後続へ渡さない。`workflow_job` の抽出と期限判定は適用しない |
| Q-010 | 後続へ渡す方式と形式 | 決定 | 渡す項目は許可リスト方式。手段は SQS 標準キュー。重複しうるため Issue #5 が冪等に処理する（J-4） |
| Q-011 | 重複時の応答 | 決定 | 処理済みの重複は200、処理中の重複は503 |
| J-5 | 診断ログ（Lambdaのロググループ）の保持期間 | 決定 | 30日（ユーザーの決定。選択肢Aを採用）。設定の根拠は `plan.md` の「決定済みの項目」 |

決定した応答のステータスと診断の分類は、`clarify.md` の「応答と診断の契約」を契約テストの入力とする。
本書の他の節にあった「未決事項とする」「clarifyで確認する」という記述は、対応する Q 番号の決定に置き換え済みである。

## 費用・運用の影響

実際の金額はリージョンと利用量で変わるため、ここでは大枠だけを示す。
単価は plan で公式の料金ページを確認して見積もる。AWS認証情報は読まない。

| 要素 | 費用の傾向 | 運用上の注意 |
| --- | --- | --- |
| API Gateway | リクエスト数に比例する従量課金。種類（Q-005）で単価が異なる | アクセスログは有効にしない（`plan.md`）。429の件数はメトリクスで見る |
| Lambda | 実行回数と実行時間の従量課金。想定は小規模 | 同時実行の上限（Q-003）で費用の上限を抑える |
| 重複排除の保存先 | 書込み回数と保持量に比例する。TTLで保持量を抑えられる | 保持期間は3日（Q-002）。オンデマンド課金で容量の指定は不要 |
| Secrets Manager | Issue #3で作成済みのSecretの月額とAPI呼び出し料金。キャッシュで呼び出しを減らせる | CloudTrailで取得を監査する |
| CloudWatch Logs | 取り込み量と保存期間に比例する | 診断に入力内容を含めないため量を抑えられる。保持期間は30日（J-5） |

- 不正な入力が大量に届く場合でも、署名検証の前にサイズ上限で拒否し、費用の増加を抑える。
- 実AWSへのデプロイは本Specの対象外であり、本Specの作業で費用は発生しない。
